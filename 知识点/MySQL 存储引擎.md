InnoDB、MyISAM、Memory、Archive、MyRocks

## InnoDB
MySQL 5.5 之后默认存储引擎。
特性：
- 事务支持
- 行级锁
- 外键约束
- 聚簇索引，表数据按照主键顺序存放
应用场景
对事务完整性要求高的应用，OLTP 系统、电子商务、金融系统等频繁更新和删除操作的场景。
缺点：
比 MyISAM 读写效率差，占用空间大。count(\*)没有 where 需要扫描全表，因为没有缓存表的总行数。

## MyISAM
MySQL 5.5 版本之前默认的存储引擎。
特性：
- 索引和数据分开存储，索引直接指向数据记录的物理地址，查询速度快，缓存了表的总行数，不带条件的 count(\*) 能够瞬间完成。
- 不支持事务
- 表级锁定
- 文件结构：`.frm`表结构定义，`.MYD`数据文件，`.MYI`索引文件
应用场景
读多写少，对事务无要求
缺点：
不支持事务和外键，并发写入能力差；宕机后数据丢失

## Memory
将所有数据存储在内存中
特性：
- 内存存储
- 数据易失性
- 表级锁定
- 索引支持：支持 Hash 索引和 B-Tree 索引
- 存储限制：对表大小有限制，不支持 TEXT、BLOB 大字段类型
应用场景
适合临时表、缓存表

## Archive
目标是存储大量历史数据和归档数据，提供了非常高的压缩比节省存储空间
特性：
- 高压缩比：使用 zlib 对数据进行压缩，压缩比可达到 10:1
- 无索引：不支持索引，查询性能差，需要全表扫描
- 写入性能低：插入高效，但由于压缩机制，吸入性能差
应用场景
数据归档和存储大量不常访问的历史数据

| 特性        | InnoDB        | MyISAM      | MEMORY     | ARCHIVE  |
| --------- | ------------- | ----------- | ---------- | -------- |
| **事务支持**  | **支持 (ACID)** | 不支持         | 不支持        | 不支持      |
| **锁级别**   | **行级锁**       | 表级锁         | 表级锁        | -        |
| **外键约束**  | **支持**        | 不支持         | 不支持        | 不支持      |
| **存储介质**  | 磁盘            | 磁盘          | **内存**     | 磁盘       |
| **数据持久性** | 持久            | 持久          | **不持久**    | 持久       |
| **崩溃恢复**  | **支持**        | 不支持         | 不支持        | -        |
| **索引**    | B+树           | B+树         | B+树, Hash  | 不支持      |
| **主要优势**  | 事务安全、高并发      | 读取速度快       | **访问速度极快** | **高压缩比** |

| **典型场景**  | OLTP系统、金融、电商  | 博客、新闻、数据仓库  | 临时表、缓存     | 日志归档、历史数 |

## MyRocks
Facebook 开发，解决 InnoDB 在大规模数据集下遇到的瓶颈，特别是**存储空间占用**和**写放大**问题。将 Facebook 开源的 RocksDB 集成到 MySQL 中。
MyRocks 基于 LSM Tree
> B+Tree：In place更新。修改一行数据，先找到这行数据的数据页 Page，读取内存，在写回磁盘，会产生随机 IO，在 SSD 上造成写放大问题
> LSM Tree：Out place 更新。数据更新是追加的，先写内存 MemTable，写满后刷到 Immutable MemTable，后台线程刷到磁盘上SSTable，过程是顺序 IO。SSTable 会形成多个 Level，后台线程会定期进行 Compaction；读取操作会查询MemTable 以及磁盘上多个 Level 的 SSTable。

MyRocks 优势：
- 高空间效率：适合数据压缩，从 InnoDB 迁移到 MyRocks，存储空间减少了 50%；无碎片化，B+ Tree 由于页分裂会产生内部碎片，LSM Tree 追加写和 Compaction 消除了这个问题。
- 写入性能高，更低的写放大：写入是顺序写入内存和磁盘，避免随机 IO；延长了 SSD 寿命。
- 灵活配置与数据过期：TTL 支持，支持为数据设置生存时间，过期数据在后台 Compaction 过程中自动清理
劣势：
- 读取性能复杂：点查询下，会查询内存和磁盘上多个文件，造成读放大，虽然有 Bloom Filter 机制优化，但读取路径比 B+ Tree 更长；范围查询，B+ Tree 叶子节点是双向链表，范围查询高效，LSM 树范围查询需要在多个 SSTable 文件中进行，性能低
- 后台 Compaction 的资源消耗：Compaction 是保证 MyRocks 性能的关键，配置不当会导致读性能下降，运维难度大
- 生态和成熟度

| 对比维度      | InnoDB (B+ Tree) | MyRocks (LSM Tree)  |
| --------- | ---------------- | ------------------- |
| **核心优势**  | 通用性强，读写均衡，稳定可靠   | **空间效率高，写入性能强**     |
| **最佳场景**  | 混合读写OLTP，对读取延迟敏感 | **写密集型，存储成本敏感**     |
| **数据结构**  | B+树              | LSM树                |
| **写入模式**  | 随机写（原地更新）        | 顺序写（追加）             |
| **读取模式**  | 高效的点查询和范围查询      | 点查询和范围查询相对复杂        |
| **空间占用**  | 较大，有碎片           | **非常小，压缩率高**        |
| **写放大**   | 较高               | **很低**              |
| **运维复杂度** | 相对成熟，易于管理        | 较高，需要精细调优Compaction |
- 如果你的应用是**通用的OLTP系统**，读写负载均衡，或者对**读取延迟的稳定性**有极高要求，**InnoDB** 仍然是首选和最安全的选择。
- 如果你的应用场景符合以下一个或多个特征，那么**MyRocks** 将是一个极具吸引力的选项：
    
    - **写密集型负载**：如物联网（IoT）数据采集、日志系统、用户行为跟踪。
        
    - **存储成本敏感**：数据量巨大，希望通过高压缩率节省大量的磁盘成本。
        
    - **使用SSD/Flash存储**：希望最大化写入性能并延长硬件寿命。
        
    - **数据有生命周期**：需要自动删除过期数据。
