| 方案                        | 原理                          | 延迟精度 | 是否分布式 | 优点        | 缺点         | 适用场景     |
| ------------------------- | --------------------------- | ---- | ----- | --------- | ---------- | -------- |
| **DelayQueue**            | JDK 阻塞队列，按延迟时间排序            | 毫秒级  | ❌ 单机  | 无依赖、实现简单  | 内存占用高、任务易失 | 单机、小数据量  |
| **Redisson DelayQueue**   | Redis ZSet 模拟 DelayQueue    | 毫秒级  | ✅     | 分布式、内存安全  | 依赖 Redis   | 分布式延迟任务  |
| **RabbitMQ 死信队列**         | 消息 TTL + 死信交换器              | 毫秒级  | ✅     | 解耦、可靠、可重试 | 配置复杂       | 企业级、微服务  |
| **Redis 键过期监听**           | 监听 `__keyevent@*__:expired` | 秒级   | ✅     | 简单、无队列    | 不可靠（丢失风险）  | 延迟通知类需求  |
| **时间轮（HashedWheelTimer）** | 轮询 + 槽位调度                   | 毫秒级  | ❌ 单机  | 高性能、低延迟   | 实现复杂、无持久化  | 高频单机调度   |
| **MQ 延迟消息**               | RocketMQ、Kafka 延迟投递         | 秒级   | ✅     | 高吞吐、可扩展   | 精度有限       | 大数据量、高并发 |
| **调度框架（Quartz/XXL-JOB）**  | 定时触发器模拟延迟                   | 秒级   | ✅     | 可管理、可重试   | 非原生延迟、配置重  | 企业级定时任务  |
| **数据库轮询**                 | 定时扫描过期任务                    | 秒级   | ✅     | 简单、可持久化   | 性能差、延迟不稳   | 低频、低并发场景 |

## Redis key过期监听
Redis 2.8 引入**keyspace notifications**。
- 内部异步任务（serverCron）在“真正删除”过期 key 时，通过 **pub/sub** 向固定频道  
    `__keyevent@<db>__:expired` 推送一条消息，消息体就是被删的 key 名。
- 客户端只要 **SUBSCRIBE/PSUBSCRIBE** 这个频道即可收到通知；**整个流程是“fire-and-forget”**，不保证 100 % 送达，也不承诺准时

| 限制点            | 说明                                      | 规避/缓解                                              |
| -------------- | --------------------------------------- | -------------------------------------------------- |
| **时间不精确**      | 过期 key 由“定时采样+惰性删除”完成，**延迟几分钟很常见** 。    | 对准时性要求高的业务（秒级关单）请改用 Redisson DelayQueue 或 MQ 延迟消息。 |
| **事件可能丢失**     | pub/sub 无持久化，客户端重连期间的所有事件直接丢弃 。         | ① 加补偿定时任务扫描数据库；② 使用 Redis Stream 替代 pub/sub。       |
| **高并发下性能差**    | 每删 1 个 key 就 1 条消息，**QPS 高时网卡/CPU 飙高**。 | 关闭不必要的通知位；或者降级到 Redisson 方案（批量拉）。                  |
| **不支持“取消/重置”** | TTL 一旦设置只能缩短，不能延长；业务取消任务无法撤回。           | 把任务 id 放 SortedSet 自己维护，可随时删除。                     |

## 时间轮（HashedWheelTimer）
为什么不用 DelayQueue？

| 问题  | DelayQueue    | HashedWheelTimer |
| --- | ------------- | ---------------- |
| 复杂度 | O(log n) 堆调整  | O(1) 哈希定位        |
| 并发  | 全局锁           | 单线程+无锁队列         |
| 内存  | 每个任务 1 个 Node | 环形数组+链表，极小       |
| 规模  | 十万级任务已吃紧      | 千万级任务仍平稳         |
海量短周期定时任务（网络框架心跳、RPC 超时、滑动窗口限流）必须把时间复杂度降到常数级，于是时间轮应运而生。
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/d6577af8b67bca29cdaadbec43aa8f7b_MD5.jpeg)
运行流程：
1. **transfer**：将“新提交任务”按哈希槽放入 wheel（批量无锁）。
    
2. **expire**：把当前 bucket 链表里的任务全部 expire()；若任务被取消则移除。
    
3. **tick++**：指针前移一格，睡眠到下一个 tick 起点。
仅 1 条 Worker 线程负责转动；任务提交方把任务扔进 MPSC（多生产者单消费者）队列即可返回，**无锁并发**。

| 场景          | 是否推荐   | 原因                          |
| ----------- | ------ | --------------------------- |
| 心跳/超时 ≤ 几分钟 | ✅ 极香   | O(1) 触发，内存友好                |
| 毫秒级精准定时     | ❌ 误差大  | tickDuration 最小 1 ms，且有调度误差 |
| 长周期任务（>1 h） | ❌ 圈数爆炸 | 需多级时间轮或外部调度框架               |
| 可取消任务       | ✅ 支持   | `timeout.cancel()` 即时从链表摘除  |
==单层时间轮只适合精度以及时间跨度比较小的情况；==

### 多层时间轮
多层时间轮分为多个，每两个轮之间是进位的关系：
- 秒级时间轮上,设有60个槽, 每两个槽之间的时间为1s.  
    
- 分钟级时间轮上,设有60s个槽,每两个槽之间的时间为1min  
    
- 小时级时间轮上,设有24个槽,每两个槽之间的时间为1h.
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/29fc9ff0fd93df3d08d603c057515de7_MD5.jpeg)

| 坑     | 说明                    | 规避                                       |
| ----- | --------------------- | ---------------------------------------- |
| 单线程阻塞 | 任务里睡 1 s，整个轮卡住        | 任务只负责抛异步，真正耗时逻辑放线程池                      |
| 实例过多  | 每 new 一个就一条线程，默认上限 64 | 全局复用单例                                   |
| 时间漂移  | 机器时钟被 NTP 回拨          | 用 `System.nanoTime()` 计算相对时间，Netty 已内置补偿 |
| 槽数太大  | 内存浪费，空转严重             | 根据最大延迟估算：槽数 = 最大延迟 / tickDuration        |
HashedWheelTimer = **环形哈希表 + 单线程指针**，  
把“定时”变成“哈希+链表批处理”，  
用 **O(1) 插入/触发** 和 **近乎零 GC** 的代价，  
换来 **千万级任务、毫秒级延迟** 场景下的极致吞吐
