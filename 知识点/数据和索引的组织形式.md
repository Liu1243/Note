## 堆组织表
 Oracle、PostgreSQL、SQL Server 数据库默认方式。
 数据行的物理存储顺序与插入顺序有关，但与任何列值（如主键）的顺序**无关**。数据是无序存放的。
 索引是独立于表数据的结构
 
| 优点 (Pros)                               | 缺点 (Cons)                                    |
| --------------------------------------- | -------------------------------------------- |
| **插入速度快**：只需找到空闲空间写入即可，无需维护数据行的物理顺序。    | **主键查询需要两次I/O**：一次读索引，一次读表数据（回表）。            |
| **二级索引（非主键索引）高效**：所有索引都指向稳定的ROWID，结构简单。 | **空间利用率可能较低**：删除和更新可能导致内部碎片 (Fragmentation)。 |
| **非常通用**，适合绝大多数应用场景。                    | 如果表经常按主键范围扫描，性能可能不如索引组织表。                    |
## 索引组织表
MySQL InnoDB 中，主键索引（聚簇索引）的实现方式就是索引组织表。
数据表本身就是一个 B-Tree 索引。数据行直接存储在主键索引的叶子节点中，并严格按照主键的顺序进行物理排序。

| 优点 (Pros)                         | 缺点 (Cons)                                   |
| --------------------------------- | ------------------------------------------- |
| **主键查询和范围扫描极快**：数据本身就是有序的，I/O开销小。 | **插入/更新/删除可能较慢**：为了维护物理顺序，可能需要移动大量数据或引发页分裂。 |
| **节省空间**：无需为数据表和主键索引分别存储，二者合一。    | **二级索引开销更大**：二级索引包含主键值，如果主键很大，二级索引也会很大。     |
|                                   | **二级索引查询性能较低**：总是需要回查主键索引，比堆表的ROWID回表慢。     |
|                                   | **必须有主键**：表结构强依赖于主键。                        |

## 哈希组织表
使用较少
数据行的物理存储位置由其某个列（哈希键）的值通过哈希函数计算得出。

| 优点 (Pros)                                              | 缺点 (Cons)                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------- |
| **等值查询（WHERE id = ?）极快**：理论上一次 I/O 即可定位数据，时间复杂度为 O(1)。 | **范围查询（WHERE id > ?）和排序查询（ORDER BY）极其低效**：因为哈希打乱了顺序，只能进行全表扫描。 |
|                                                        | **哈希冲突**：不同的键值可能产生相同的哈希值，导致数据堆积在同一个桶内，查询性能会退化。                |
|                                                        | **空间管理复杂**：需要预估哈希键的数量来确定桶的数量，不易扩展。                            |
|                                                        | **哈希键的选择非常关键**：键值必须是均匀分布的，否则会加剧哈希冲突。                          |
