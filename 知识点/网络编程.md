## 同步阻塞
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/1c7fdaee122f7a6df15aa271c090a5ec_MD5.jpeg)
accept 与 read 系统调用都会阻塞。
单线程：单个 socket 阻塞，会影响到其他 socket 处理。
多线程（一个客户端一个线程处理）：在客户端较多时，会造成资源浪费，同一时刻可能只有几个 socket 就绪。线程调度、上下文切换、内存占用会成为瓶颈。
## 同步非阻塞
==解决 accept 阻塞问题==
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/d2f25dffbce762765d7db6122dfc1d38_MD5.jpeg)
accept 是非阻塞的，返回的 accept_fd 是就绪的 socket 数量，将就绪的 socket fd 添加到 fd_list 中。
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/7edee0f69786f7fd53f220417c4a4635_MD5.jpeg)
从 OS 层面解决了阻塞问题。
优点：单个 socket 阻塞不会影响到其他 socket。
缺点：需要不断遍历进行系统调用，有上下文切换开销。
## select
==解决大量系统调用问题==
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/0bdb5e75eb77a6a75a41a0c71e2aefdb_MD5.jpeg)
fd_set是 bitmap 实现的，其中 readfds、writefds、execpfds 是用户态与内核态共用的，用户态语义是要监听的 fd，内核态返回的则是就绪的 fd。
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/26b7016226f28eddd48bf18fd3ae0002_MD5.jpeg)
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/403bee498cbc770169282c553ec01fa2_MD5.jpeg)
将 socket 是否就绪检查下沉到内核空间，避免大量的系统调用。可以返回有事件就绪，但是无法告知是具体哪个 fd。
优点：不需要每个 fd 都进行一次系统调用，解决了用户态内核态频繁切花问题。
缺点：
- 单进程监听 FD，默认 1024
- 每次调用需要将 FD 从用户态 copy 到内核态
- 不知道具体哪个文件描述符就绪，需要 On 遍历全部 fd
- 入参的 3 个 fd_set 集合需要每次调用前重置
## poll
==解决监听 fd 1024数量限制==
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/c5b8070c4b3ba633e2239a9bac84fb8d_MD5.jpeg)
通过 pollfd 结构体，解决了fd 监听数量 1024 的限制，也不需要入参集合重置。
## epoll
==解决 fd 用户态内核态 copy 问题，以及具体 fd 就绪的信息==
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/75b43f25337ddea8eeb881ba87727a6f_MD5.jpeg)
epoll_create 创建一个 epoll 对象 。
epoll_ctl 在 epoll 对象上新增、删除以及更新 epitem。
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/ef4203cea2e127bc3b4328f0b4e51b6e_MD5.jpeg)
epoll_wait 等待 epoll 上的就绪事件
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/3e01e1b32bc6e5a53afe3045ef04287b_MD5.jpeg)
ep_poll_callback 是回调函数，用于软中断将 epitem 放入就绪队列。
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/c401dbb57be7c5e6746efe5238b51cb6_MD5.jpeg)
高效处理高并发下的大量链接，有着优异的性能。
缺点：
- 跨平台性不好，只支持 linux
- 相较epoll，select 更加轻量可移植
- 监听连接数和事件较少场景下，select 更优
### LT、ET
LT：水平触发（默认）。epoll_wait 检测到事件后，如果该事件没有被处理完，后续每个 eopllwait 调用都会返回该事件。需要每次都检查事件的处理情况，影响性能。
ET：边缘触发。检测到事件后，只会在当次返回该事件，不管事件是否被处理完毕。

## 网络模型
### Thread-based 架构模型
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/db7347b14d6406f74349a7fdee0e7fa3_MD5.jpeg)
对应阻塞式 IO 模型。
### Single-Reactor 单线程网络模型
一个 epoll 对象称为一个 Reactor
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/4d0c4d91c1405050d73870c033d4b8bf_MD5.jpeg)
业务逻辑处理会影响到 acceptor 的处理，导致不能支持大量链接。
### 改进：Single-Reactor 线程池模型
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/f6c3ee9b9f59f052ce587212e7dc8fe8_MD5.jpeg)
将业务逻辑剥离到线程池 worker threads 处理，职责分离，但是在高并发场景下，acceptor 仍会受到影响。
### Multi-Reactor 多线程模型
![](%E7%9F%A5%E8%AF%86%E7%82%B9/attachments/3365c80632a553f6272e08ae33912fa7_MD5.jpeg)
逻辑划分mainReactor、subReactor，mainReactor 负责与 client 链接，subReactor 负责业务逻辑处理。
### 改进：Multi-Reactor 多进程网络模型
将 mainReactor、subReactor 分为多个进程。
经典实现是==nginx==
